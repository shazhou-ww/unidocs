# PSD 区域编辑设计

日期: 2026-09-01
分支: feat/psd-image-edit（区域编辑是它的后续工作）
状态: 设计待评审（未开始实现）
前置: `docs/superpowers/specs/2026-09-01-psd-image-edit-design.md`

## 1. 问题

`editPixels` 今天把**整个图层**交给图像模型。真实案例：一张 3404x2000（6.81 Mpx）
的人像图层，指令是"把帽子换成头发加白色蝴蝶结"。结果三处不对：

1. **构图被改了。** 人物变大、位置偏移。qwen-image-edit 不是局部修补工具 ——
   给它整张图和一个语义很重的编辑，它会重画整个主体并顺手重新构图。
2. **胶片颗粒没了。** 链路是 6.81 Mpx → 压进像素预算 → 压进字节预算 → 模型
   重绘 → 拉回原尺寸。颗粒是高频细节，一次下采样就被平均掉，模型不重建它，
   上采样也救不回来。
3. **保护机制失效了。** 差异蒙版本该让未改动区完全透明、露出原层字节。但原图
   带颗粒、模型输出平滑，逐像素差在**整张图上**都远超阈值 16，蒙版于是覆盖
   几乎全图，等于不存在。

### 1.1 为什么文件那么大（实测）

用户的 JPEG：3553x2000 = 7.11 Mpx，1.19 MB，相对原始 RGB 压 17.9 倍。
我们送出的 PNG：3404x2000，13.02 MB，只压 1.57 倍。差 11 倍。

原因是 JPEG 有损、PNG 无损，而**颗粒是 PNG 的最坏情况**。实测（1200x800 平滑
渐变，逐级加噪）：

| 颗粒强度 | PNG 体积 | 相对原始 RGB（2.9 MB） |
|---|---|---|
| 0% | 0.16 MB | 压 18 倍 |
| 10% | 2.19 MB | 压 1.3 倍 |
| 30% | 2.41 MB | 1.2 倍 |
| 60% | 2.50 MB | 1.2 倍 |

**只加 10% 颗粒，PNG 就涨 14 倍。** PNG 靠邻居预测 + 压缩残差，随机噪声不可
预测；JPEG 做的第一件事就是量化掉高频，而颗粒几乎全是高频。

于是形成一个讽刺的循环：想保住的质感正是让文件大 11 倍的原因；文件大触发
下采样；下采样恰好把这个质感抹掉。

### 1.2 一个被实测否定的假设

曾怀疑是宽高比拉伸：适配器把模型输出无条件 `resample` 到源尺寸，若模型返回
的比例不同就会形变。**实测否定**：输入 1360x800（1.700）→ 输出 1344x800
（1.680），差 1.2%；返回图中心的正圆包围盒 588x597（比例 0.985，仍是圆）、
圆心正在画面中心、四角标记全在。模型贴着输入宽高比选最近的支持分辨率，
既不压扁也不裁切。

早先"1184x896"的观测来自 1.33 比例的输入，拿它外推 1.70 是错的。
**没有拉伸 bug，也不该"修"它** —— 按当时的设想去居中裁剪，反而会丢掉真实内容。

### 1.3 另一个被实测否定的优化

曾以为送 RGBA 白白多带一个恒为 255 的 alpha 平面，改送 RGB 能省 25%。实测：
在带颗粒的图上 **RGB 反而比 RGBA 大 4~7%**，只有平滑图才省 21%。此项不做。

## 2. 决策

四个决策，均由用户拍板：

1. **矩形由模型作为工具参数传**，不改跨包协议。模型今天就能从指令里的
   `<<selection bounds=[...]>>` 读到用户框的范围，也可以先 `getPreview` 再自己
   收紧。代价是模型从降采样预览估坐标可能框偏。
2. **向外扩一圈给上下文，只贴回原矩形。** 扩出来的那圈只给模型看，不落盘。
3. **`rect` 可选，缺省整层。** 整层是退化情形，代码只有一条路径。堵"模型直接
   拿整层去"这个坑靠提示词和工具描述，不靠阈值。
4. **裁剪在查询侧，合成在 effect 侧**（方案 A）。

### 2.1 为什么不把区域下推进 ImageEditor 端口

`EditRequest` 加 rect 看似最面向未来，但会**把文档几何泄漏进图像端口**。这个
端口今天能换 provider，正因为它只说一句话："给你一块像素和一句指令，还我同
尺寸的像素" —— 它不知道图层、画布坐标、选区。裁剪是消费方的事。端口里已经有
`mask?: Coverage` 和 `capabilities.mask` 三态，等真有支持蒙版的 provider，那才
是它该走的口子。

### 2.2 为什么不在 effect 侧裁剪

改动更小，但**两个 DO 的内存峰值仍是整层** —— 而那正是要消除的东西。

## 3. 数据流

```
模型: editPixels {layerId, instruction, rect:[t,l,b,r]}
  |
  +- 扩边：rect 按 PAD_RATIO 外扩，与图层 bounds 求交 -> sendRect
  +- ctx.query(getLayerPixels {layerId, rect: sendRect, maxPixels})
  |     +- Editor: renderRegion(孤立单层文档, sendRect)
  |        只渲染这一块，内存正比于矩形而非整层
  +- editor.edit(sendRect 的像素, instruction)      <- 适配器一行不改
  +- 在 sendRect 尺寸上 softenMask -> applyCoverageToAlpha
  +- 裁到 rect
  +- ctx.writeBlob(rect 尺寸的 PNG)
  +- op: generative_fill { layer.bounds = rect, parentId, index+1 }
```

`renderRegion` 不是新机制：`renderLayer` 本身就是
`renderRegion(孤立单层文档, layer.bounds, ctx)`。

**关键性质**：新图层的 bounds 就是 rect，所以**矩形之外原层完全不被覆盖**。
这是几何事实，不依赖任何阈值 —— 这正是"丝毫不差"能成立的地方。

### 3.1 丝毫不差的边界

- **矩形之外**：结构性保证，逐字节等于原层。
- **矩形之内**：做不到。凡是经过模型的像素都会被重编码，只能靠差异蒙版尽量
  还原。这一点不该对用户含糊。

区域编辑真正的价值不是"矩形内更准"，而是**把不可控的范围从整层缩到一个小
矩形**，同时让矩形内不必下采样（颗粒得以保留），差异蒙版拿到的输入才可比。

## 4. 扩边与贴回

**扩多少。** 左右**各**外扩 `PAD_RATIO x 宽`，上下**各**外扩 `PAD_RATIO x 高`
—— 所以宽高各涨 `1 + 2 x PAD_RATIO` 倍（R=0.25 时是 1.5 倍，面积 2.25 倍）。
用比例而非固定像素，才对不同尺寸的选区都成立。

`PAD_RATIO = 0.25` 是**待验证的起点，不是实测值**。本设计不为它编造依据。
用户场景的账（按颗粒图 1.5 倍压缩估）：

| | 尺寸 | 像素数 | PNG 估算 |
|---|---|---|---|
| 头部选区 | 700x900 | 0.63 Mpx | ~1.3 MB |
| 扩 0.25 | 1050x1350 | 1.42 Mpx | ~3 MB |
| 扩 0.5 | 1400x1800 | 2.52 Mpx | ~5.3 MB |

两者都在 4.19 Mpx 像素预算与 9 MB 字节预算内，**都不触发下采样**。取值待真实
文档上验证。

**边界截断。** 扩完与图层 bounds 求交。选区贴边时 pad 变不对称，无妨。

**返回尺寸。** 端口后置条件保证适配器还回的与送进的严格同尺寸，所以
`result.pixels` 一定是 sendRect 大小，裁回 rect 只是已知偏移的数组切片，
不涉及缩放。违反了就是适配器 bug，已有断言拦截。

**顺序（唯一容易写错的地方）**：

```
适配器返回 sendRect 尺寸的 pixels + changed
  -> 在 sendRect 尺寸上 softenMask（膨胀 + 羽化）
  -> 在 sendRect 尺寸上 applyCoverageToAlpha
  -> 最后裁到 rect
```

不能先裁再羽化：`softenMask` 要膨胀，在裁剪边界上缺一半邻域，羽化出的过渡带
贴回后就是一道可见暗边。先在完整 sendRect 上算，裁掉的只是本就不落盘的那圈。

**不做额外的矩形边缘羽化。** 在 rect 边界再加渐隐，会在"改动一直延伸到边界"
时把模型新内容与原内容半透明混合，出一圈鬼影。该羽化的是"改动区与未改动区
的交界"，`MASK_SOFTEN` 已在做。

**代替方案：把边界被切如实报给模型。** 落盘前检查差异蒙版在 rect 四条边上的
覆盖度，某条边上有相当比例像素被判为改过时，在返回文本里写明（例如"改动延伸
到了矩形右边缘，38% 被切；如果结果有硬边，用更大的 rect 重试"）。这比默默羽化
诚实：硬边的成因是 rect 给小了，该让模型知道并有机会修正。

## 5. 错误处理与降级

**坐标系前提**：`rect` 用**画布坐标**，与 `<<selection bounds>>`、图层 `bounds`、
`renderRegion` 全都一致（`renderLayer` 就是把 `layer.bounds` 直接喂给
`renderRegion`）。求交是直接的，无需坐标转换。

| 情况 | 处理 |
|---|---|
| `rect` 不是四个数 | `fail()` 返回可读消息，模型重试；不抛异常 |
| `rect` 顺序反了（top>bottom 或 left>right） | **拒绝，不自动交换**；消息写明期望 `[top,left,bottom,right]` |
| `rect` 与图层 bounds 完全不相交 | 拒绝，消息里给出图层真实 bounds |
| `rect` 部分超出图层 | 求交，正常情形 |
| `rect` 覆盖整层 / 不给 rect | 今天的行为，同一条代码路径 |
| `refused` / `timeout` / `provider_error` | 不变：`ops: []`、不涨版本、原因回传 |
| `changed === null` | 降级为**整个 rect 替换**（不再是整层），`maskDerivation: "none"` |
| 裁到 rect 后蒙版全黑 | 返回 `ops: []`，告知模型改动全落在矩形之外 |

**为什么不自动交换顺序。** 模型很可能把 `[left,top,right,bottom]` 写成我们要的
`[top,left,bottom,right]`。自动纠正会把一个语义错误变成"语义正确但位置完全错"
的矩形，然后静默改错地方。宁可拒绝并说清期望顺序。

**不设最小尺寸阈值。** qwen 的真实下限从未测过，编一个阈值就是又一个没有依据
的常量。让它过去反而诊断更好：图太小时 API 自己报错，经 `provider_error` 原样
回给模型，信息量比自造阈值大。记为待测项。

**不产生空图层。** 裁到 rect 后蒙版全黑，说明模型只改了扩边区。落盘会得到一个
全透明图层污染图层树，因此返回 `ops: []` 并说明原因。

**顺带的好处**：`MAX_EDIT_SOURCE_PIXELS` 现在作用在 sendRect 而非整层。今天
8 Mpx 以上的图层会被直接拒绝，有了区域编辑，**只要选一小块就能编辑任意大的
文档**。这不是特意设计，是把守卫挪到正确粒度后的自然结果。

## 6. 测试策略

本次会话每一个逃逸的缺陷都是从"合成图"这个洞里钻出去的，因此这一节写得重。

### 6.1 合成测试能钉住的

- **矩形几何**：外扩、求交、裁回偏移。纯算术，手推黄金值。
- **操作顺序**：必须 `羽化 -> 烘 alpha -> 裁剪`。让蒙版在裁剪边界附近非平凡，
  断言过渡带两侧对称 —— 顺序写反就不对称。
- **拒绝路径**：格式错、顺序反、不相交、裁完全黑。
- **落地 bounds**：新层 bounds 必须等于 rect。判别性验证：改成落在图层 bounds
  上，这条必须失败。
- **端到端**：扩展 `edit-pixels-e2e.test.ts`，走真的 `apply`，断言源层 blob 哈希
  不变**且**新层 bounds 是 rect。

### 6.2 合成测试钉不住的（三个盲区）

**熵。** 所有 fixture 都是平滑渐变，16.8 Mpx 压出 0.3 MB，真实照片密 40 倍 ——
这就是 10MB 上限在测试里从没被碰到的原因。
> 对策：加共享的 `grainyPixels(w, h, grain)` 到 `src/testing/`。**凡断言体积或
> 差异蒙版的测试，一律用带颗粒的 fixture。**

**内存。** vitest 跑在 Node 里，堆远宽于 128 MB isolate，没有单测能触发 OOM。
> 对策：**别测"会不会爆"，测"分配了多少"**。断言 `getLayerPixels` 带 rect 时
> 只渲染那一块（返回尺寸等于 sendRect，且 `renderRegion` 收到的是 sendRect）。
> 内存正比于矩形是可测的，OOM 不可测。

**真实模型行为。** 会重新构图、会抹掉颗粒、会贴着输入宽高比 —— 全靠打真实 API
才知道，单测永远不可能知道。
> 对策：`live: true` 契约跑，手动执行并写进文档；继续把真实响应录成 fixture。
> **明确规矩：任何声称"实测"的注释必须能指到一次真实调用。**

### 6.3 为这次故障专写的测试

失败链是"颗粒 -> 差异蒙版覆盖全图 -> 退化成整层替换"。造一张带颗粒的源图，
让桩 editor 返回轻微平滑过的同一张图（模拟模型重渲染），断言蒙版覆盖比例 ——
这条测试若早存在，问题上线前就会暴露。

但更该钉死的是真正要卖的那个保证：

> **无论矩形内的差异蒙版退化成什么样，矩形之外的像素必须逐字节等于原层。**

不依赖任何阈值，是几何事实，也正是 §3.1 的"丝毫不差"能成立的理由。必须有测试，
且必须判别性 —— 把落地 bounds 改回整层，它就得红。

### 6.4 不给猜出来的常量写"正确性"测试

`PAD_RATIO = 0.25` 是待验证的起点。测试只钉**算术**（给定比例 R 正确外扩并截到
边界），**不断言 0.25 这个值是对的**。同理不设 rect 最小尺寸阈值，也就没有对应
测试。

## 7. 本轮范围

做：`getLayerPixels` 加 `rect`；`editPixels` 加 `rect` 参数与扩边/裁回/落地；
边界被切的回报；`grainyPixels` fixture 工具；上述测试；提示词更新（强调给 rect）。

不做：跨包协议改动（请求体仍是 `{instruction}`）；把 rect 下推进 `ImageEditor`
端口；lasso/wand 等非矩形选区（`Region.maskId` 的通路留着，本轮不接）；
JPEG 上传。

## 8. 待验证 / 已知缺口

- `PAD_RATIO` 的取值，需在真实文档上验证。
- qwen 对极小输入的行为下限，从未测过。
- **JPEG 上传作为有条件的后备**：对**不透明**图层可行，能在预算内送满分辨率；
  对**带透明**图层不行 —— JPEG 无 alpha，而哨兵法把 alpha 编码成品红，色度
  子采样与块效应会在透明边界糊掉哨兵色，`recoverAlpha` 的容差 24 会误判边缘。
  另需注意：JPEG 伪影进入模型输入后会出现在输出里，从而拉大与干净原图的差异，
  间接放大差异蒙版。区域编辑之后基本不需要此项。
- 非矩形选区（lasso/wand）：UI 的 `Region` 已备好 `maskId` 通路，但蒙版字节如何
  跨包送达（`api.ts` 注释提到的"carries a mask through CAS"）需要独立设计。

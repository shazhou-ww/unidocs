tenant UI 重设计 · 2026-09-10

决策与未决项

对齐依据：docs/design/platform-v0/agent-mediated-document-collaboration.md。 视觉沿用 docs/design/unidocs-mock.css。

已定

01 · thread 身份 = 位置锚定

一个 thread 对应文档里一个锚点，长期存在。ping 序列只由人追加、可跨版本；Agent 一条 pong 累计确认到某个 ping 水位。 open := latestPingSequence > acknowledgedPingSequence，因此 UI 里没有「解决 / 重新打开」按钮 —— 追加 ping 就自动 re-open。 对应架构文档 §5.1–§5.3。

02 · 选中 thread = 主区分屏对照

左栏渲染该 ping 的 base version（下称「基版」，灰底、只读徽标、绿色高亮 ping location），右栏渲染 current，最右仍是 316px 讨论面板。不做浮窗方案。

右栏分三种情况：
· 有 pong —— 金色高亮 result location
· ping 就写在 current 上 —— 不重复高亮，标「暂无改动 · 与左栏同一版本」
· ping 基于旧版本 —— 那段话还在则用灰底虚线标出对应位置（明说不是 Agent 的改动）；已被改写掉则不高亮，换一条说明（§5.4 / §8.2）
03 · 同一 thread 内逐条 ping 可切版本

点 thread 默认展示最新一条 ping 的基版；点 thread 内某条具体 ping，左栏切到那条 ping 的基版和它的高亮。ping 卡片上标出各自的 v 号。 对应 §5.4：ping 不要求基于 current，基于历史版本的 ping 依然有效。

04 · 内容对人永远只读

分屏两栏都不可编辑。人的唯一产出是 ping，版本只由 Agent 提交。 现有 mock 里的源码编辑器、双栏 Markdown 编辑、以及用户自己 commitDraft 推新版本的路径全部移除；顶栏改为一枚「只读 · 内容由 Agent 编辑」标识。

05 · 版本下拉 = 独立的全屏只读回看

与「选中 thread → 分屏对照」是两条独立路径。全屏回看模式收起讨论面板，换上版本历史面板，同时呈现 base parent 链与 comment provenance 块，并提供「把 current 移到这一版」入口 —— 该动作必须写审计（§3.3）。

06 · 评论逐条发送，Agent 后台自动接手

用户视角只有「评论」：选中一处、写一句、发送，随时可以往同一处追加。没有「统一提交 N 条」这一步 —— 界面上不出现批次，也不出现 ping/pong 这两个词。

发送由人完成，标记这一条说完了；发出即写入平台成为该 thread 的一条 ping，平台把新增 ping 推给 operator hook，Agent 在后台自动开始处理（§6.3），不需要用户再点一次「交给 Agent」。 Agent 什么时候攒批、一次处理几条，是它自己的排队策略，用户不感知。

输入框都由动作触发，不常驻：
· 新评论 —— 在正文里选中一段文字 → 浮出「添加评论」 → 展开输入框
· 追加 —— 选中的那一处底部有「回复」按钮 → 点开才出输入框 → 发送或取消
· 面板上没有常驻的输入区，也没有底部的批次提交条

界面词 ↔ 协议词：
· 一条评论 = 一条 ping
· Agent 的一条回复 = 一条 pong（可累计回应同一处的多条评论）
· 「待回复 / 已回复」= 由水位派生的 open 状态，不是一个可切换的标志
07 · 草稿留在本地；已发送的评论不可改，改＝新提一条

没发送的评论是草稿，只在本地、Agent 看不到，每个位置一份、可以同时存多份：写到一半切去看别处不会丢。 面板顶部显示「N 条未发送」，筛选里有「未发送」一档；收起来的草稿在该处卡片底部留一块黄色虚线块。

已发送的评论不可编辑也不可删除 —— 协议里 ping 追加即存在（§5.1），而且它可能已经在被 Agent 处理。 所以「修改」是这样一条路径：原文留在原地并标出此刻状态（水位未覆盖 = 正在执行，已覆盖 = 已处理）， 你改的那份压回草稿并注明「改自评论 N」，发送时作为同一处的新一条追加 —— 于是它落在水位之后，该处自动从「已回复」变回「待回复」。

没有做、也不打算在这一层做的：撤回已发送的评论。协议层没有定义「撤回」是什么，要做得先回到协议。

未决

OPEN ISSUE 编辑型 ping（架构文档 §11.2）绕过，后面再看怎么实现

架构文档允许用户在 View 里直接改字、挪对象，发布时由文档类型组件编码成一条编辑型 ping。本阶段一律不实现：所有渲染面只读，画布上不画任何直接操作入口。

重新捡起时要先答的问题：
· 编辑型 ping 落在哪个 thread —— 新建位置锚定 thread，还是并入已有锚点？
· 用户看到的是即时编辑，但 Agent 可能不照做。「我改了但没生效」怎么在 UI 上表达？
· 编辑型 ping 与意见型 ping 在同一 thread 里如何排序、如何各自渲染卡片？
· 编辑期间 current 前移，本地草稿的基版已陈旧，如何提示？
未画 子文档批注的归属与转发

§9.1：评论默认归属于用户当前所在的 View，主文档 Agent 可把工作转发给子文档。 那么在主文档里对一张嵌入图片提的 ping，thread 显示在主文档面板还是跳到子文档？转发后原 thread 的 pong 怎么写？本轮未画。

未画 窄屏与移动端

分屏对照在 1440 宽下成立。现有 mock 对移动端直接给「请在电脑或平板上查看」。窄屏下分屏怎么降级 —— 上下堆叠、还是回退成单栏加版本切换 —— 本轮未定。

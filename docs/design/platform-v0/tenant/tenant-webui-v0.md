## 1. 界面词与协议词

协议词表原本用 ping / pong 指代这两条消息序列，现已改为 comment / reply：人写的那条东西
就是一条评论，它的序号照样驱动水位，没有任何机制含义丢失。于是界面词和协议词在这两项上
重合，不再需要翻译。

剩下需要翻译的只有 thread 和 current 这两个不出现在产品界面上的协议词：

| 界面词 | 协议词 |
| --- | --- |
| 一处（讨论） | 一个位置锚定的 thread |
| 待回复 / 已回复 | 由水位派生的 open 状态，不是可切换的标志 |
| 当前版本 | current version |
| 草稿（未发送的评论） | 本地状态，还不是一条 comment |
| 评论所基于的版本（下称基版） | 该 comment 的 base version |
| Agent 这次改动的位置 | reply result location |

`reply` 这个名字看不出「可累计」：**一条 reply 确认到某条 comment 为止，因此通常一次覆盖
同一处的多条评论**，不是一对一回复。协议层靠 `respondThroughCommentIdx` 这个字段名和各处
描述把它讲清楚。

## 2. 已定

### 2.1 thread 身份 = 位置锚定

一个 thread 对应文档里一个锚点，长期存在。comment 序列只由人追加、可跨版本；Agent
一条 reply 累计确认到某个 comment 水位。

```text
open := latestCommentSequence > acknowledgedCommentSequence
```

因此界面上没有「解决 / 重新打开」按钮：追加评论就自动 re-open。对应协议 §5.1–§5.3。

### 2.2 选中一处 = 主区分屏对照

左栏渲染该 comment 的基版（灰底、只读徽标、绿色高亮 comment location），右栏渲染
current，最右仍是 316px 讨论面板。不做浮窗方案。

右栏分三种情况：

- **有 reply**：金色高亮 result location；
- **comment 就写在 current 上**：不重复高亮，标「暂无改动 · 与左栏同一版本」；
- **comment 基于旧版本**：那段内容还在，则用灰底虚线标出对应位置，并明说这不是 Agent
  的改动；已被改写掉则不高亮，改为一条说明。

第三种情况是本设计里最需要说清楚的一类：平台不做语义迁移，也不因为 current
前移就作废旧版本上的评论，由 Agent 判断它是否仍然适用（§5.4 / §8.2）。它的常见成因
不是用户自己改的，而是 Agent 处理**别的**一处评论时顺带改掉了这段内容。

### 2.3 同一处内逐条评论可切版本

点一处，默认展示最新一条评论的基版；点其中某一条具体评论，左栏切到那条评论的基版
和它的高亮。评论卡片上标出各自的版本号，落后 current 时另标「基于 vN · 已过 N 版」。
对应 §5.4：评论不要求基于 current，基于历史版本的评论依然有效。

### 2.4 内容对人永远只读

分屏两栏都不可编辑。人的唯一产出是评论，版本只由 Agent 提交。

现有 mock 里的源码编辑器、双栏 Markdown 编辑、以及用户自己 `commitDraft`
推新版本的路径全部移除；顶栏改为一枚「只读 · 内容由 Agent 编辑」标识。

### 2.5 版本下拉 = 独立的全屏只读回看

与「选中一处 → 分屏对照」是两条独立路径。全屏回看模式收起讨论面板，换上版本历史
面板：左侧竖线是 base parent 链（每版只有一个），虚线块是 comment provenance
（这一版回应了哪些评论、它们各自基于哪个版本）。两者不能互相替代。

面板同时提供「把 current 移到这一版」入口，并在旁注明该动作会写入文档级审计（§3.3）。
查看的就是 current 时，这两个按钮不出现。

### 2.6 评论逐条发送，Agent 后台自动接手

用户视角只有「评论」：选中一处、写一句、发送，随时可以往同一处追加。**没有
「统一提交 N 条」这一步**——界面上不出现批次。

发送由人完成，标记这一条说完了；发出即写入平台成为该 thread 的一条 comment，平台把
新增 comment 推给 operator hook，Agent 在后台自动开始处理（§6.3），不需要用户再点一次
「交给 Agent」。Agent 什么时候攒批、一次处理几条，是它自己的排队策略，用户不感知。

输入框都由动作触发，不常驻：

- **新评论**：在正文里选中一段内容 → 选区上方浮出「添加评论」 → 展开输入框；
- **追加**：选中的那一处底部有「回复」按钮 → 点开才出输入框 → 发送或取消；
- 面板上没有常驻输入区，也没有底部的批次提交条。

### 2.7 草稿留在本地；已发送的评论不可改，改＝新提一条

没发送的评论是草稿，只在本地、Agent 看不到，**每个位置一份、可以同时存多份**：写到一半
切去看别处不会丢。面板顶部显示「N 条未发送」，筛选里有「未发送」一档；收起来的草稿在
该处卡片底部留一块黄色虚线块。作品列表的卡片上也标出未发送条数。

**已发送的评论不可编辑也不可删除**——协议里 comment 追加即存在（§5.1），而且它可能已经
在被 Agent 处理。所以「修改」是这样一条路径：

1. 原文留在原地，并标出此刻状态：水位未覆盖它 = **正在执行**，已覆盖 = 已处理；
2. 你改的那份压回草稿，注明「改自评论 N」；
3. 发送时作为同一处的**新一条**追加——于是它落在水位之后，该处自动从「已回复」变回
   「待回复」。

没有做、也不打算在这一层做的：撤回已发送的评论。协议层没有定义「撤回」是什么，要做得
先回到协议。

## 3. 文档类型

同一套布局覆盖两种位置类型，差别只在 location 的采集与渲染：

| | Markdown | PSD |
| --- | --- | --- |
| locationType | `unidocs.markdown.text-range/v1` | `unidocs.psd.layer-region/v2` |
| 采集方式 | 选中一段文字 | 画布上框选区域 / 选中图层 |
| 左栏高亮 | 文本 range 底色 | 绿色选区框 + 底部图层条标出命中图层 |
| 右栏高亮 | 文本 range 底色 | 琥珀色结果框 |

新增文档类型只需要提供这两端能力，分屏、版本、讨论面板与状态机不变（§12.2）。

## 4. 作品列表

卡片底部暴露该作品的讨论状态（`N 处待回复` / `Agent 已回复 N 处` / `暂无讨论`）。
顶部一条「Agent 最新回复」，并在文案上明确 **reply 只表示已处理，不表示你已接受**——
不同意就在原处追加一条评论。纯 reply（只回复、没有产生新版本）在这里用中性色标识，
不能穿版本号的衣服。

## 5. 未决

### 5.1 编辑型 comment（§11.2）—— 本阶段整节绕过

协议允许用户在 View 里直接改字、挪对象，发布时由文档类型组件编码成一条编辑型 comment。
**当前阶段一律不实现**：所有渲染面只读，不提供任何直接操作入口。

重新捡起时要先回答：

- 编辑型 comment 落在哪个 thread——新建位置锚定 thread，还是并入已有锚点？
- 用户看到的是即时编辑，但 Agent 可能不照做。「我改了但没生效」怎么在界面上表达？
- 编辑型与意见型 comment 在同一 thread 里如何排序、如何各自渲染？
- 编辑期间 current 前移，本地草稿的基版已陈旧，如何提示？

### 5.2 子文档评论的归属与转发

§9.1 规定评论默认归属于用户当前所在的 View，主文档 Agent 可把工作转发给子文档。
那么在主文档里对一张嵌入图片提的评论，显示在主文档面板还是跳到子文档？转发后原
thread 的 reply 怎么写？本轮未画。

### 5.3 窄屏与移动端

分屏对照在 1440 宽下成立。现有 mock 对移动端直接给「请在电脑或平板上查看」。窄屏下
分屏如何降级——上下堆叠，还是回退成单栏加版本切换——本轮未定。

### 5.4 待确认的小项

- comment 就写在 current 上时，分屏左右两栏是同一版，信息量为零，是否自动收成单栏。
- 移动 current 的审计只在提示条上给了一句说明，没有专门的审计日志面板，是否需要。
- comment provenance 的跨版本连线目前只画成虚线块，没有画成真正的连线（行高不定，
  画出来会是假的精度）。
